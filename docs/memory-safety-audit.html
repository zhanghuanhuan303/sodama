摘要

本报告回应「审计 unsafe 代码的内存泄漏风险」的专项要求：对 loader 与数据面（eBPF）中全部不安全语法点做逐处审读，按 UB 风险 / 内存泄漏 / fd·资源泄漏 / 有界保留 四类给出判定，并把「查过且没有问题」的核销清单完整列出（§5），使结论可复核、范围可证。

总体判断：

  • 未发现无条件成立的用户态堆内存泄漏。unsafe 部分以 syscall 包装（socket/ioctl/epoll/pipe/splice/mmsg）为主，fd 所有权整体规范（前置 raw < 0 检查、OwnedFd 收尾、成对删插），7 个 unsafe impl aya::Pod 与内核侧结构逐字段同位。
  • 发现 3 项高优先、4 项中优先、13 项低优先/加固、2 项附带（非内存类）。三项高优先分别为：reactor 管道回收不排空导致的跨会话数据串流（H1）；拨号墙钟看门狗 arm/disarm 不对称导致活跃 socket 被定时掐断（H2）；legacy splice 路径捕获 fd 号码而非句柄导致的 fd use-after-close（H3）。
  • 「持有期无界」而非分配器泄漏是本次的主要泄漏形态：组世代线程（M1）、UDP NAT 会话表（M2）、透明回包 socket 表（M3）、退出残留的内核钩子（M4）。与第一阶段结论（分配器高水位、非泄漏，见 devlog §3）一致。
  • H2 与 M1 都与既有记录直接呼应：H2 是 §9「探测线程泄漏」修复（墙钟看门狗）引入的副作用；M1 与 P37「探测/额度治理」动机冲突（旧世代线程仍在探测）。

结论纪律：本报告以静态审计为主——除 cargo clippy 为实跑外，v1.0 条目均基于逐行代码审读与依赖源码（aya 0.14.0）对照；v1.1 增补 §8 生产实况比对（2d5h39m 真实运行数据），其中 H2 被实锤、M4 被证伪降级，其余发现生产零暴露。每条发现标注置信度与复核指引；修复建议的实施状态见 §9。

2 · 高优先发现

H1 · reactor 回收 pipe 不排空 → 跨会话数据串流 高

位置
reactor.rs:1049-1083（destroy 回收）、reactor.rs:142-155（put_pipe）、reactor.rs:383-433（drain）、对照 reactor.rs:1170-1176（sweep 的空闲释放有 pending==0 检查）
类别
跨会话数据串流（资源生命周期缺陷；非内存泄漏、非 UB）
置信度
机制=高；「缓存复用后先行写出」的时序命中=中（未运行时复现）
// reactor.rs:1076-1082  destroy()：无条件把两条 pipe 放回 worker 本地缓存
if let Mode::Splice { c2u, u2c } = &mut sess.mode {
    for d in [&mut *c2u, &mut *u2c] {
        let p = std::mem::replace(&mut d.pipe, [-1, -1]);
        put_pipe(&mut self.pipe_cache, p);      // ← 不排空、不问 pending
    }
}
// 对照 drain() 的注释（reactor.rs:385）："不变量：释放仅在 pending==0 时发生"
// 对照 sweep()（reactor.rs:1172）：if d.pending == 0 && d.pipe[0] >= 0 { ... }

机理：put_pipe 把管道（容量 PIPE_SZ=1 MiB，reactor.rs:34）直接放入 worker 本地缓存（上限 8 对），管道内可能是刚从 socket splice 进来的、尚未 drain 给对端的字节。而 destroy 的进入条件并不蕴含 pending==0：

  • finished()（reactor.rs:577-585）在 dead 时为真；dead 由 EPOLLERR 或任一方向 fill/drain 报错置位（reactor.rs:529-534）——典型如客户端 RST 时 u2c 方向仍可能有~1 MiB 未送达响应；
  • sweep() 的 stop 分支（janitor 强制回收，reactor.rs:1199-1207）与 rearm 失败分支（reactor.rs:1128-1131）同样不检查 pending。

后果：后续会话从缓存取到该管道后（arm_pipe，reactor.rs:157-168），fill 把新数据追加在残留字节之后，drain 按 pending.min(CHUNK) 从管道读端取——FIFO 先取出的是上一会话的残留字节并发送给新会话的对端（跨连接数据污染/隐私暴露）；同时 pending 记账与管道实存失配，半关闭时点（maybe_half_close，reactor.rs:451）可能提前触发导致丢数。生产默认开启 reactor（reactor::enabled() 仅在 SODAMA_NO_REACTOR 设置时关闭），RST 属日常事件，命中概率应按「worker 缓存复用 × 非对称收尾」评估为现实存在（推断）。

建议修法（未实施）：destroy 中若任一方向 pending > 0 或 eof 不一致，则先非阻塞排空至 EAGAIN（丢弃）再入缓存，或直接 close 该管道不入缓存；亦可给 put_pipe 加「入缓存前断言两方向 pending==0，否则 close」的硬约束，把不变量固化到唯一入口。

复核指引：读 reactor.rs:136-168 / 383-433 / 1049-1083 / 1128-1131 / 1160-1180 / 1425-1440；运行时验证：加「destroy 时 pending>0 计数」临时探针，在压测中制造客户端 RST 观察计数与串流日志。

H2 · 拨号墙钟看门狗 arm/disarm 不对称 → 活跃 socket 被定时掐断 高

位置
武装 outbound.rs:181（marked_tcp_connect 内）· 解除 outbound.rs:1227（仅 dial_tcp）· 缺失点 outbound.rs:1640-1646（dial_udp）
类别
行为缺陷（活跃连接被 shutdown）+ fd/线程有界保留（≤deadline）
置信度
代码事实=高；运行时后果=中高（若被同线程后续 disarm 意外掩盖则减轻，见下）
// outbound.rs:179-181  marked_tcp_connect：每次 TCP 拨号都武装墙钟看门狗
set_sock_timeouts(stream.as_raw_fd(), Some(timeout))?;
arm_dial_watchdog(stream.as_raw_fd(), timeout);   // 到点对 dup 执行 shutdown(SHUT_RDWR)

// outbound.rs:1224-1227  dial_tcp：拨号结束即解除（成败都解除）
let r = self.dial_tcp_inner(target, timeout);
disarm_dial_watchdog();

// outbound.rs:1640-1646  dial_udp：**没有** disarm_dial_watchdog()
let r = self.dial_udp_inner(target, timeout);

r

机理与波及面：看门狗线程分片睡眠（20ms 粒度）至 timeout 后，对该 socket 的独立 dup 执行 shutdown(2)（outbound.rs:207-241）。disarm_dial_watchdog 全仓库仅 dial_tcp 与测试调用（已核实）。因此以下路径在拨号成功后的 timeout（拨号层默认 RELAY_DIAL_TIMEOUT_MS=5000）到点会被**主动掐断**：

  • VLESS / VMess 的 UDP-over-stream（outbound.rs:1698/1729 经 marked_tcp_connect 建立长连接，承载 UDP NAT 转发与 UDP 健康探测）——5s 后连接被切断；
  • DNS 上游持久连接（DoT/DoH）（dnsup.rs:342/359 直用 marked_tcp_connect）——CONNECT_TIMEOUT 到点被切断，之后复用「看似存活」的持久连接会失败；
  • 订阅拉取（subscribe.rs:116）与 bootstrap DNS（bootstrap.rs:136）——一次性连接被提前/滞后关闭，主要影响是看门狗线程 + dup fd 存活至 deadline（有界）。

另注意：CUR_DIAL_WATCH 为线程本地且新武装会覆盖旧值——旧看门狗的 cancel 标志不再可达，即使同一线程稍后发生一次 dial_tcp，也只解除最新一次武装（outbound.rs:240/245-251）。除非同线程恰好覆盖，否则上述拨号必被掐断；生产上 UDP NAT 主要走 ss/hy2/tuic（不触发此路径）时症状会被掩盖（推断）。

建议修法（未实施）：把 disarm 改为 RAII guard（作用域结束自动解除，覆盖所有拨号入口）；或在 dial_udp/dnsup/subscribe/bootstrap 各拨号出口补 disarm_dial_watchdog()；同时为嵌套拨号把「单个槽位」升级为栈/代际标记，使 disarm 只作用于本次武装。

复核指引：读 outbound.rs:207-251 / 1224-1241 / 1640-1646 / 1690-1745、dnsup.rs:342-380；运行时验证：以 VLESS 节点起 UDP NAT 会话，抓 ss -tnp 观察 5s 周期性 RST，或临时把看门狗日志开关打开。

v1.1 生产实锤（§8）：30s 逐秒扫描显示每条约 223.5.5.5:443 的连接恰好存活 3 秒（= CONNECT_TIMEOUT）后消失、端口每次更换（≈ 1.4 万次重连/天）；exchange_https 的「丢弃连接重试」把首试失败静默吞掉，故日志无痕、错误计数不涨。已修复（§9）。

H3 · legacy splice 上方向线程持 raw fd 号码 → fd use-after-close 高

位置
捕获 main.rs:3052 · 线程使用 main.rs:3171-3181 · 原始 socket 析构点 main.rs:3246（函数返回）；对照 outbound.rs:1243-1257（DialedStream.socket 为 kill dup）
类别
fd 生命周期误用（use-after-close：写错对象或静默截断；非 Rust UB）
置信度
机制=高；触发前提=非默认开关（SODAMA_NO_REACTOR=1，实验室 A/B 路径）+ 方向不对称收尾
// main.rs:3052  只捕获 fd "号码"（i32），不是句柄
let upstream_fd = socket.as_ref().map(|s| s.as_raw_fd());
// main.rs:3173-3181  上方向（client→上游）独立线程
let up_dst = upstream_fd;                       // i32 拷贝进 move 闭包
... splice_pump(c_read.as_raw_fd(), dst /* up_dst */, ...)
// main.rs:3245-3246  下方向泵在本线程结束后：pump_done(); } ← socket（kill dup）在此析构，
//                    fd 号被关闭；而线程保活的是 handle.upstream（另一个 dup，保 description 不保号码）

机理：两泵设计（main.rs:3156-3162，为修复历史「泵线程泄漏」而引入）保证连接收尾在两个方向都结束后才 relay_finish；handle 内的 upstream dup 在此期间使 file description 保活。但上方向线程使用的 up_dst 是 DialedStream.socket（kill dup）的号码，该对象由 handler 函数栈持有，函数返回即关闭该号码。触发序：下方向先结束（上游半关闭/先出错）而客户端仍在上传 → handler 返回、号码关闭 → 上方向线程随后 splice 到该号码：未被复用则 EBADF（上传静默截断、且 Fatal 分支置 spliced=true 不落回退泵）；被并发 accept/dial/pipe2 复用则把客户端数据**写进无关对象**（跨连接数据污染）。

建议修法（未实施）：上方向线程改用 handle.upstream（RELAY_CONNS 内 dup，保活至双泵结束）的 as_raw_fd()；或将 socket（Option<TcpStream>）直接 move 进闭包、在闭包内取号；并顺带为「关闭前断言无在用 raw fd」建立约定。

复核指引：读 main.rs:3035-3061 / 3155-3246、outbound.rs:1243-1257；运行时验证：SODAMA_NO_REACTOR=1 下构造「上游先 FIN、客户端继续发送」的半关闭用例，观察上传截断/交叉写。

M4 · 退出残留：cgroup 钩子（所有内核）与 <6.6 的 tc 过滤器；重启 EEXIST 静默降级 低（v1.1 修正）

v1.1 生产比对修正（降级）：aya 0.14 的 cgroup attach 在内核 ≥5.7 走 bpf_link_create（aya-0.14.0/src/programs/cgroup_sock.rs:77-95），link 随进程退出自动解绑；生产（6.12.92）三个世代连续「6/6 挂载成功、零 EEXIST/失败日志」，直接证伪了「重启静默降级」的预测。本节结论仅在 <5.7 内核（aya fallback 到 bpf_prog_attach）或 <6.6 + 非正常退出（tc netlink 过滤器）时成立。详见 §8。

位置

类别

置信度
高（残留与 EEXIST 为内核/aya 语义；「重启后具体表现」建议实测一次）

机理：（a）bpf_prog_attach 到 cgroup 的引用由 cgroup 持有，进程退出不会自动摘除（与内核版本无关）；graceful_shutdown 直接 exit(0)，Ebpf 永不 Drop。（b）TC 过滤器：aya 仅在内核 ≥6.6 走 TCX（fd 关闭即原子摘除）；<5.17–6.5 走 netlink，摘除需要 NlLink::detach（RTM_DELTFILTER），而该路径在本进程永不触达（mem::forget(link) + exit；注：clippy 已证实 forget 的对象无 Drop，真正 link 由 Ebpf 持有，故「forget 造成每轮泄漏」不成立，问题在 退出路径从不 detach）。

建议修法（未实施）：启动时对目标 cgroup 先执行一次「清空该类钩子」（bpf_prog_detach2/查询后 detach）再 attach；或在 graceful_shutdown 中显式 detach 全部 HOOKS/tc 链接（保留 exit 仅作兜底）；并把 EEXIST 从「仅告警」升级为「先 detach 再重试」。

复核指引：main.rs:1860-1915 / 1791-1812 / 5656-5676，aya tc.rs:236-246/486-501、links.rs:400-420；运行时验证：重启 daemon 后 bpftool cgroup tree 观察旧程序是否仍在。

L2 · set_len(UDP_SLOT) 的容量守卫写法错误（当前不可达） 低

位置：outbound.rs:649-656。if cap < UDP_SLOT { slot.reserve(UDP_SLOT - cap); }——reserve(additional) 保证 capacity ≥ len + additional，当 len < cap 时不足以保证容量 ≥ UDP_SLOT，随后 set_len 可能越过 capacity（破坏 Vec 不变量）。当前所有槽均来自 PoolBuf::zeroed(UDP_SLOT=65600)（走大档、cap≥128KB，且 resize 已零初始化），该分支不可达、无实际 UB；但守卫语义应写为 reserve(UDP_SLOT - len) 或直接 resize(UDP_SLOT, 0)。一旦未来有调用方传入 65536-cap 的槽（main.rs:2053 已有此规格缓冲）即成为真 UB。复核：outbound.rs:636-695、bufpool.rs:41-71/87-107。

L3 · DNS 后台刷新单飞表在 panic 路径不清（key 永久卡死） 低

位置：dns.rs:681-688（begin_refresh/end_refresh，注释写明「无论成败，必须调用」）、main.rs:6449-6488（end_refresh 在线程体末尾，无 catch_unwind/RAII）。机理：刷新线程体内任何 panic 将跳过 end_refresh → 该 key 永久留在 refreshing（String 量级）且该 (scope,qname,qtype,up) 之后永不再后台刷新（功能静默退化）。触发需 panic（上游交换均有超时，概率低）。建议：以 RAII guard 承接 end_refresh。复核：dns.rs:675-693、main.rs:6430-6490。
