00 · 决策摘要

给没时间读完全文的人：五条结论 + 七个待拍板项（节 08 可勾选）。

现状判断

复杂度来自内核与运维边界，不是 Go 语言

65k 非测试行里，59% 在 control/（38.6k）：BPF 生命周期、路由编译、DNS 控制器、TCP/UDP 会话、netns/tc、offload。这些规模由「内核矩阵 × 协议细节 × 热重载」决定，换语言不会消失。

收益判断

Rust 的收益集中在四个面

① 用户态转发路径无 GC 尾延迟；② 报文/DNS/协议解析的内存安全；③ 类型系统承载路由 IR 与配置 schema；④ 单静态二进制与更小的运行时占用。不包含「数据面变简单」——eBPF 的 verifier 约束与内核兼容是同一堵墙。

最大风险

outbound 协议栈是真正的深水区

代理协议实现（ss/vmess/vless/trojan/hysteria2/tuic/juicity/anytls…）在同组织的独立仓库 daeuniverse/outbound，规模未知且不在本仓库。Rust 生态只有部分协议有成熟 crate。它决定「生产可替换」是否成立。

已验证路径

「C 数据面 + Rust 控制面」今天就能走通 已实测

mini-dae 用 aya 0.14 加载并挂载 TCX 钩子、进 daens setns、建 IP_TRANSPARENT socket 入 sockmap、写 LPM/Array/Hash map，proxy/direct/block 分流、本机流量、热重载、单写者、故障注入八用例在标准与单臂两种拓扑下端到端通过。数据面程序本身改用 aya-ebpf 需要 nightly（本环境被网络策略拦住，未验证）。

建议主线（2026-10-03 修订：内核切片先行）

按「内核切片先行（K0–K3）→ DNS → 转发面 → 协议栈 → 运维面」推进。关键是把「内核攻坚」定义成纵向切片：数据面（规则 VM / LPM / 双 epoch / conntrack）+ 最小驱动（routing 子集编译 + 钩子集合管理）+ 最小对拍器（map dump + 包级 e2e）。生态接入走契约级/进程级边界（配置 DSL、订阅格式、状态面；可选「Go 当协议后端」过渡一跳），不用 cgo/FFI。详见 ADR-0009。

部署形态结论（详 4.5 / 4.6）

常驻进程 + eBPF 分流，但不接管 direct 数据面。即「接管所有流量的决策，只接管需要代理的数据」。eBPF 数据面是 per-netns 单例、只能有一个 owner（supervisor）；用户态 worker 只持有连接。第一版单进程多线程，需要隔离时再拆 supervisor + workers。故障语义默认 fail-open（TCX 随进程退出摘钩），隐私敏感场景可加心跳死区开关。

01 · 项目全景

1.1 定位与设计哲学

dae 是 Linux 上的高性能透明代理网关：在 tc eBPF 层完成流量分流，让 direct 流量走内核三层转发（Real Direct），proxy 流量才进入用户态或内核 offload 路径。分流判据覆盖域名、源/目的 IP、端口、L4 协议、IP 版本、进程名、MAC、DSCP。

三个设计支点决定了它的全部复杂度：

  • 分流发生在报文进入协议栈之前——所以 direct 流量几乎没有额外开销，但也意味着所有判据必须在 eBPF 里可计算（域名要靠主动 DNS 关联或嗅探）。
  • 内核数据面与用户态控制面强耦合——规则以「编译产物」形态进 map，热重载是双 epoch 槽切换，状态（conntrack / 路由缓存 / 回程绑定）都在 map 里。
  • 面向长期运行的网关场景——netns 生命周期、janitor、事件限流、溢出报告、内存上限、systemd 集成，占了 control/ 相当比例。

2.1 数据面 control/kern/tproxy.c 4,403 行 C · 23 程序 · 24 map

职责

  • 分流：14 个 tc 程序覆盖 lan/wan 的 ingress/egress 与单臂双角色；用 bpf_loop 跑用户态编译出的 match_set 规则数组。
  • 重定向：改目的 MAC → 写 skb->cb → bpf_redirect 进 dae0/dae0peer；回程按 redirect_track 还原 MAC 并送回原接口。
  • 交付：dae0peer 上 bpf_sk_assign 给 tproxy socket；已建立 TCP 靠 fwmark+local 路由。
  • 状态：TCP/UDP conntrack（含路由缓存）、routing handoff、domain 位图、cookie→进程名。
  • offload：sockmap 双 socket 直连转发 + 背压保险丝 + 字节记账。

复杂度来源

不是「C 难写」，而是：内核版本矩阵（bpf_loop≥5.17、redirect_peer 的 CVE 门槛、netkit vs veth）、verifier 约束（栈 512B、循环、指针追踪，因此有大量 per-CPU scratch 与 __noinline 拆分）、并发语义（单写者绑定、内存序取舍、epoch 双槽）。

Rust 落位

  • 程序本体：两条路——保持 C（同 dae，零风险）或用 aya-ebpf 写 Rust。后者需 nightly + -Z build-std，并把 verifier 友好写法（栈预算、循环上界、指针收敛）重学一遍。
  • ABI 单一事实源：建 dae-ebpf-shared（no_std）同时被数据面与用户态引用，替换 dae 现在「C 定义 + JSON 规格 + Go 生成器」三处同步的做法。
  • 加载与生命周期：aya 的 TCX（内核≥6.6）让钩子随进程退出自动摘除，比 netlink 模式少一整类残留 bug（dae 用 28.5KB 的 netns_cleanup 测试来防这类问题）。

已实测 5 个 TCX 钩子（host ns 4 + daens 1）的挂载与卸载、跨 netns 的 map 共享、sk_assign 交付，全部在 mini-dae 验证。

3.3 值得原样保留的四个机制

① 双 epoch 规则槽

热重载不中断数据面：写另一槽 → 切 active 指针。Rust 版用户态可用 ArcSwap 思想，内核侧保持双槽，语义不变。

② 单写者回程绑定

redirect_track 只允许绑定所有者续租，2s 陈旧窗口防抢注。这是被真实攻击逼出来的设计（tproxy.c:2177 注释），不要「优化」掉。

③ offload 背压保险丝

sockmap 直连 + pause 表 + 字节记账的闭环，解决「内核队列积压时切回用户态不丢包」。需要等价的采样与控制回路。

④ 进程名从 argv 读

cgroup hook 里用 CO-RE 读 task_struct.mm.arg_start + bpf_loop 找可执行名，比 comm 可靠。数据面若重写，这是最容易写错的 CO-RE 代码之一。

重写必须一起搬的「隐性契约」（漏一个就变成难查的行为差异）
  • daens 的回程路由配方：169.254.0.11/32 + default via 169.254.0.1 + 静态邻居 + accept_local=1 已实测
  • fwmark 0x8000000 → table 2023 → local default dev lo；以及控制面 socket 的 SO_MARK 隔离
  • sysctl 组合：ip_forward、rp_filter=0、tcp_early_demux=1、disable_ipv6/forwarding（dae0）等 13 个键
  • netkit vs veth 的选择条件、bpf_redirect_peer 的 CVE-2025-37959 版本门槛
  • IPv4-mapped-IPv6 的五元组归一化（redirect_track 的 key 语义）

04 · 目标 Rust 架构

4.1 设计原则

  1. 边界照抄既有的无环依赖：现有 component/ 之间基本单向，直接映射为 crate 依赖即可，不要发明新分层。
  2. ABI 单一事实源：map 布局、枚举、常量只有一处定义（共享 crate），用户态与数据面同时引用，替换掉 dae 的三处同步。
  3. 热路径零分配：所有 per-packet/per-connection 结构预分配或来自 arena；Bytes/BytesMut 贯穿解析层。
  4. 显式状态机：连接生命周期、netns 生命周期、reload 阶段都用类型状态机表达，消除靠注释与测试守住的隐式约束。
  5. 可对拍：每个纯逻辑 crate 都要能用 Go 版当 oracle（配置、路由编译产物、DNS 语义、订阅解析）。

4.2 Workspace 与 crate 切分

4.3 运行时与并发模型

方案 A · tokio 多线程（建议起点）

控制面（配置/重载/netlink/指标）用 tokio；转发热路径用专用线程池跑 splice，或投递到内核 offload。

风险低 生态最全、与现有语义最接近，便于先拿到正确性。

方案 B · thread-per-core

每核一个 runtime（monoio/glommio）+ SO_REUSEPORT + shard 化连接表，共享内存为零、无跨核锁。

收益高但需实测 复杂点：与 netns 切换、sockmap 协调、janitor 跨线程回收。

内存模型

per-connection arena + 固定大小 buffer pool；Bytes 零拷贝贯穿 DNS/嗅探；热路径禁止 Vec 增长与 Arc 克隆。

直接收益 消除 GC 尾延迟与堆抖动（dae 有专门的内存上限/THP 处理代码，说明这确实是痛点）。

netns 亲和：Rust 要比 Go 做得更干净

dae 用 runtime.LockOSThread() + netns.Set()（control/netns_utils.go:264,496）把 goroutine 钉在处于目标 netns 的 OS 线程上。这条路径在 tokio 下不可行：task 会在 worker 线程之间迁移，线程序号的 netns 对 task 不成立。

替代方案是 per-netns socket 工厂：socket 的 netns 在 socket() 创建时即确定，之后任何线程都可以正常使用（connect/send 的路由查找都走 socket 自己的 netns）。因此只需一个常驻在目标 netns 的专用线程按需创建 socket，把 fd 交给 tokio 任务即可，不要求任务本身具备 netns 亲和。这消除了 dae 那类「忘记解锁/线程漂移」的整类 bug（Go 侧用 netns_cleanup_test.go、listener_netns_test.go 等大量测试来守）。

4.5 部署形态：常驻 worker + eBPF 分流

目标形态是：一个常驻进程持有 eBPF 数据面并完成分流，只把需要代理的数据交给用户态 worker。这里有两个方向相反的概念，必须先掰开：eBPF 分流 意味着 direct 流量不进用户态；接管所有流量 意味着所有包都进用户态。二者只能有一个作为默认路径。

维度A · eBPF 分流（建议）B · worker 全接管C · TUN + 用户态 TCP/IP 栈
direct 流量开销一次内核路由查找（零用户态）两次拷贝 + relay + 2×socket 操作用户态协议栈处理每个包
代理流量tproxy → worker，或 sockmap 内核 offload同左同左
故障域部分功能降级（direct 仍可用）整机断网整机断网
平台仅 Linux（eBPF + tc + netns）仅 Linux跨平台（macOS/Windows）
适用场景网关 / 软路由（dae 场景）全量审计、按连接 QoS/整形非 Linux、需注入或改写报文
不要把 B 当默认

除非需求是「必须在用户态看到每一个包」，否则不要选 B：direct 的成本从一次内核路由查找变成两次拷贝 + 用户态 relay，BitTorrent/游戏 NAT 这类场景会退化（dae 文档专门解释过为什么不做全接管），且单点故障从「部分功能降级」变成「整机断网」。若确实需要全量可见（审计/DLP），正确做法是 eBPF 镜像一份给旁路进程，而不是把 worker 串在所有路径上。

数据面所有权：per-netns 单例

  • 程序加载、钩子挂载、map 所有权只能有一个 owner（supervisor）。多个进程各挂一套会互相覆盖；同一 tc hook 上的多个程序是按优先级串行执行的，语义会立刻失控。
  • map 用 bpffs pin 共享（dae 已有 pin 目录与清理逻辑：control/bpf_purge.go、bpf_stub.go 的 pin 清理）。
  • tproxy listener socket 由 supervisor 创建并放入 sockmap，再通过 fd 继承（fork 或 SCM_RIGHTS）交给 worker；所有 worker accept() 同一个 listening socket 即可。sockmap 存的是 socket 引用而非 fd，bpf_sk_assign 交付后由任意一个 accept 者取走 —— 这比「每 worker 各建 listener + SO_REUSEPORT」干净得多。

4.6 常驻内存与故障语义

内存要分三块账管

用户态堆
连接状态 + buffer：预分配 buffer pool + arena；用 cgroup MemoryMax 兜底（替代 Go 的 GOMEMLIMIT 自动推导），池化上限显式化。
内核 BPF map
conn_state/redirect_track/LPM trie 的条目数与单条大小决定锁定内存；dae 用 bpf_conn_state_map_size 之类的开关暴露给用户，Rust 版应升级为显式预算模型（按最大并发连接数推算并在启动时校验 memlock）。
page cache
geosite/geoip 20+ MB；按需加载 + madvise。dae 甚至提供 disable_thp 选项，说明 THP 撐大 RSS 是真实投诉。

systemd 部署契约（dae 现有 unit 可直接沿用）

  • Type=notify（Rust 侧用 sd-notify）
  • ExecStartPre=dae validate：配置不合法不开机；Rust 版同样把 validate 做成独立子命令
  • Restart=on-abnormal + RestartSec=5s + StartLimitBurst=5/300s：把崩溃循环限住
  • LimitNOFILE=1048576、LimitNPROC=4096、OOMScoreAdjust=-100
  • 冷启动成本：静态二进制毫秒级；真正的开销是 BPF 加载 + 规则编译 + geosite 解析（dae 实测冷缓存 0.08s–0.5s）→ 做预编译产物缓存与预热

故障语义（部署形态里最该先拍板的一件事）

钩子方式daemon 挂掉会怎样性质
TCX（内核 ≥6.6，dae 首选；tc_hook_set.go:199）bpf_link 随进程关闭而摘除 → 分流消失，流量回落为普通转发 已实测（mini-dae 进程退出后钩子自动消失）fail-open 不断网，但代理规则「泄漏」

worker 化的演进路径（结论）

  1. 第一版：单进程多线程——tokio 控制面 + 专用 relay 线程池 + per-netns socket 工厂；把 worker 边界先做成任务边界。
  2. 需要进程级隔离时：supervisor + N workers——listener fd 继承、map bpffs pin 共享；worker 无状态可随时重启。
  3. 容器化成为主场景时：per-netns worker——每个 netns 独立数据面与 daens；注意 map 是全局的、listener 必须在对应 netns 内创建。

拆进程的收益（崩溃隔离、独立重启、CPU 隔离）在「eBPF 已承担主路径」的前提下是有限的，而代价（fd/netns/map 共享复杂度）是真实的。因此不要把 worker 化当成第一优先级。

5.3 DNS 与解析路径

零拷贝 wire

现状 Go 侧多轮 decode/encode + 分配。Rust 版：收到报文直接在原 buffer 上做 name 解压视图（借用而非拷贝），仅在改写 TTL/EDNS 时才复制。收益：P99 与分配压力双降。

缓存结构

分片 LRU + 每 shard 独立单飞（singleflight）；负缓存/乐观缓存语义照搬 dae（有大量回归测试可对拍）。moka 或自研分片 LRU。

上游连接复用

Go 版已有 HTTP 客户端代际管理与 DoQ owned-conn；Rust 版用 quinn 连接池 + h2 multiplex，代际切换用 ArcSwap 原子替换。

与数据面的耦合

域位图发布目前是逐条 map update。可改为批量更新 + 代际号，让一次 DNS 应答写入更少的 syscall。

5.4 内存、并发与工程效率

无 GC 尾延迟

网关场景对 P99 敏感；Rust 消除 GC 停顿与堆预留。dae 已有 disable_thp、内存上限相关代码，说明 RSS/抖动是真实运维问题。

静态数据竞争检查

Send/Sync 让「janitor 持锁时发包」这类问题在编译期暴露——dae 用多个专门测试文件守这类 bug。

启动与常驻

静态 musl 二进制、无运行时预热；容器镜像更小、启动更快，适合网关侧容器化部署。

构建链

现状：go generate + bpf2go 两段构建，eBPF 对象与二进制版本需人工保持一致。
改法：build.rs 调 clang 编译 C 对象（或 aya-ebpf），产物 include_bytes! 进二进制，单一 cargo build 出全量。

错误与可观测

thiserror/anyhow 分层 + tracing span 让「一次 reload 失败」能完整还原调用链；配置错误带源码 span。

差分测试与 fuzz

Go 版编成 dae-oracle 对拍：配置归一化输出、BPF map 内容（bpftool map dump JSON）、DNS 响应字节、订阅解析。cargo-fuzz 直接打 DSL / DNS wire / 嗅探。

明确不建议做的「优化」
  • 不要在 Rust 里重写内核已有的能力（自己实现拥塞控制、重写 IP 栈）——dae 的 offload 已经证明「能下沉就下沉」。
  • 不要动单写者回程绑定、epoch 双槽、pause 保险丝这三个安全/稳定性设计；它们是故障换来的。
  • 不要以 DNS 全自研 wire 解析为第一版目标：先用成熟库对齐语义，再在有基准的情况下替换热点路径。
