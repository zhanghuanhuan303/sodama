# ADR-0007：优先级——配置 + 路由先行

- **状态**：**被 [ADR-0009](./ADR-0009-kernel-track-first.md) 取代（2026-10-03）**——顺序改为内核切片（K 轨道）先行。本文保留作为决策演进记录。
- **对应决策点**：D7（已修订）
- **相关**：ADR-0005（配置兼容）、主文档 07（路线图）

## 背景

三个候选起点各有诱惑：

- **配置 + 路由**：纯用户态、无需 root、可用 Go 版逐条对拍；
- **数据面 + 钩子生命周期**：dae 最核心的技术，需要 root 与内核矩阵；mini-dae 已验证最小闭环；
- **DNS 引擎**：`control/` 最大子系统（controller 近 5k 行）；
- **性能基准**：用数据驱动优化取舍。

## 决策

**先做配置 + 路由（P1），但以「对拍基建（P0）」为前提。**

具体顺序与门槛：

1. P0：Go 版编成 `dae-oracle`；建立差分测试框架（配置归一化、规则编译产物、DNS 字节、map dump）；netns e2e 基座（沿用 mini-dae 的 lab 思路）。
2. P1：`dae-config` + `dae-routing`，验收标准 = 随机 1k 组规则与 Go 版逐条一致。
3. 之后按 P2（数据面 ABI）→ P3（DNS）→ P4（转发面）→ P5（协议栈）→ P6（运维面）→ P7（收敛）。

## 理由

- 配置/路由的 fan-in 最高（`common/consts` 113、`config` 58、`pkg/config_parser` 56、`component/routing` 34），被 DNS 与数据面同时依赖；先做能解锁最多后续模块。
- 「无需 root」意味着**可以在 CI 里全自动回归**，建立「对拍 → 通过」的节奏成本最低。
- 数据面虽然核心，但 mini-dae 已证明其最小闭环；把它放在对拍基建之后做，能直接复用 oracle 与 lab。
- 性能基准不是起点而是 P7 的输入：在主路径已由内核 offload 承担的前提下，过早优化收益不确定（风险 R9）。

## 后果

- 正面：P1 可独立交付并立刻被真实使用（`validate`/`export`）；后续每步都有对拍保护。
- 负面/代价：数据面（最"性感"的部分）排在第二，前 6–9 周看不到内核侧成果；需要用 mini-dae 这类实验维持技术纵深。
- 需注意：对拍基建本身要按产品级质量做（它决定后续所有验收的可信度）。

## 验证方式

- P0 验收：一条命令拉起三 netns 环境并能对拍 `dae validate/export` 输出；
- P1 验收：见上；失败用例必须能定位到「Go 的行为」还是「Rust 的行为」。

## 修订条件

若上线压力要求优先保证内核侧能力（例如只能先替换特定场景），可新写 ADR 调整顺序，但不应跳过 P0 对拍基建。
