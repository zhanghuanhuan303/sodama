# ADR-0006：交付范围——只做 dae 本体

- **状态**：已采纳（2026-10-03）
- **对应决策点**：D6
- **相关**：ADR-0001（目标定位）

## 背景

上游生态中存在两层交付物：

- **dae**：单机网关本体（本仓库）——eBPF 数据面 + 控制面 + CLI + systemd；
- **daed**：独立工程，提供 API/面板/多节点管理。

Rust 重写的范围若包含 daed，工作量与接口面几乎翻倍，且会引入 Web/API 层的大量非核心工作。

## 决策

**只做 dae 本体。** daed 相关的兼容层（最小只读 API 或 gRPC）作为可选后置项，在 dae 本体可用之后按需评估。

实现约束：

1. 核心 crate（`dae-*`）不得依赖任何 HTTP/API 层；CLI（`daed` 二进制）只承载 run/reload/validate/export/suspend/sysdump/trace；
2. 若将来需要 API，另建 `daed-api` crate 消费 `dae-runtime` 的只读状态，而不是把 API 需求反向渗入核心。

## 理由

- 网关本体的价值与风险都在内核侧；API 层不阻塞核心价值，且后补不会造成返工（只要核心保持「状态可查询」的接口）。
- 保持 crate 边界「无 HTTP 依赖」让核心更容易测试（无网络、无序列化）。

## 后果

- 正面：范围可控；核心 crate 保持精简；对拍与集成测试只需要 netns 环境。
- 负面/代价：现有依赖 daed 的用户无法直接替换；面板/多节点能力需要另行规划。
- 中性：如果将来要做 API，`dae-runtime` 需要暴露状态快照类型（本 ADR 建议提前把「运行态快照」设计成纯数据结构，便于同时服务 CLI 与 API）。

## 验证方式

- `cargo tree` 检查核心 crate 无 HTTP/Web 依赖；
- 功能验收以「单机网关场景」为准（LAN 分流、DNS、规则、热重载、offload）。

## 修订条件

若产品方向确认需要多节点/面板，新写 ADR 定义 API 边界与鉴权模型。
