# ADR-0001：目标定位——生产质量、分批交付

- **状态**：已采纳（2026-10-03）
- **对应决策点**：D1（`../architecture-decision.html`）
- **相关**：ADR-0006（交付范围）、ADR-0007（优先级）

## 背景

被重写的对象是约 **65k 非测试行 Go + 外部协议栈 + 事实上的 40k 行行为规范（测试）**。一次性对齐全部功能（含协议栈与运维面）在人力上不现实；而纯学习型复刻又会让「能跑通」与「能替换」之间的差距在后期集中爆发。

## 选项

| 选项 | 说明 |
|---|---|
| A 学习型复刻 | 覆盖可以不全，目的是看懂技术 |
| B 生产可替换 | 最终在真实网络取代 Go 版，全功能 + 运维面 + 协议栈 |
| **C 混合（采纳）** | **按生产质量写核心闭环，分批交付；协议栈与运维面后置** |

## 决策

采用 C。判定标准：

1. 所有交付的代码按生产标准写（错误处理、可观测、可回滚、有测试与对拍），不接受「临时脚手架」进入主干；
2. 功能按路线图 P0–P7 分批，每批必须**可运行、可对拍、可停**；
3. 协议栈（P5）与运维面（P6）是可选项，不做「未完成协议栈就整体不可用」的设计。

## 理由

- 沉没成本风险最高的是「做到一半发现要重来」。分批 + 可停的策略保证任何时点停下都保留价值。
- 核心闭环（配置 → 路由 → 数据面 ABI → DNS）本身已经是 dae 的绝大部分领域复杂度，值得按生产质量做。
- 「生产质量」与「分批交付」不矛盾：前者约束**每批的完成度**，后者约束**范围**。

## 后果

- 正面：范围可控；每批有独立验收；对拍基建（P0）一旦建成，后续批次边际成本下降。
- 负面/代价：必须维护「哪部分已落地」的状态说明，否则外部使用者会误以为功能对等；需要明确写出「当前不支持」清单。
- 中性：最终是否达到与 Go 版功能等价，取决于 P5 的结论，不由本 ADR 保证。

## 验证方式

- 每批交付时检查：是否有对拍/集成测试、是否能独立部署、是否有回滚路径；
- 每批结束时更新主文档 07 节的进度状态与 README 的功能对等表。

## 修订条件

若 P5 的协议栈收敛结论证明「无法在合理工期对齐」，则本 ADR 的「生产可替换」目标需要重新评估，应新写 ADR 取代。
