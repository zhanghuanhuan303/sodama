§2 方法学

2.1 环境与口径

  • 全部测试在 netns 拓扑（client ns — 网关 — WAN ns）内完成，与公网路径无关；机器已切换到不经软路由的网络（wlan0 直连），对 netns 数字无影响。真实公网口径（real.sh）见 §11（2026-10-17 订阅到位后补测）。
  • 夹具：lab/bench_io（48 MB × 4 流全双工；lat 500 次）、conn_scale（hold/churn）、echo_server（万级连接）。direct 口径受夹具 ≈24.5 Gbps 上限约束（64×1 MB 口径可达 38.7 G）。
  • ss 上游为 ssserver 1.25.0（shadowsocks-rust）；Python 上游有 GIL ≈2.4 Gbps 上限，仅作功能对照。
  • CPU 列 = 被测进程 utime+stime 增量（realfile /proc/pid/stat，10 ms 粒度）；RSS/线程为负载期值。
  • CPU governor 固定 performance（空闲 800 MHz 会导致短促负载的采样偏低；默认 powersave 下首轮偏低 10–20%）。

2.2 与 atlas 的差异（为什么数字不会逐字相同）

  • atlas 表 2 的 sodama 行（threads=11）实测于 M1–M2 时代构建；本轮为 A2 收口构建（threads=31，M4 reactor 线程模型），线程/内存基线与若干路径性能已不同。
  • atlas 图 4（五方 RSS @2 000）的柱标签与正文折算值存在对不上的迹象（图内 sing-box=298.1 MB 与正文"sing-box ≈47 KB/连接"矛盾）；本轮实测口径为 dae≈153 KB、mihomo≈88 KB、v2ray≈73 KB、sing-box≈43 KB、sodama≈16 KB，与 atlas 正文一致（§5.1）。

2.3 流程坑（本轮踩到）

dae 就绪等待：run.sh 启动后固定 sleep 2.5 即开测。首轮 all 中 dae 尚在加载（RSS 41 MB、无 relay 日志），流量被"假公网兜底路由"无实现直通 → 读出 24.6 G / CPU 0 的假象。复跑（验证 RSS 已增、relay 日志出现）后为 12.3–13.2 G / CPU 380–420 ms。判定方法：vless 行与 direct 行数字近似（≈夹具上限）或 CPU≈0 即为假象，须复测。

口径备注：常驻 200 连接在 t≈295 s 被 relay janitor 按空闲超时回收（日志 200 条「回收空闲连接」，holder 进程本身仍存活）。此后负载实际为 churn + 周期负载 + 采样。该回收是设计行为，但意味着 atlas 口径「200 条长连接贯穿全程」在本轮未严格成立——建议 soak 夹具给 hold 连接加心跳或显式设置 relay_idle_timeout，使长稳同时压住“空闲长连接”维度。

§8 回归与修复专题

8.1 eBPF 对象被宿主验证器拒载（已修复）

现象：按当前 main 构建的 eBPF 对象在本机 6.18.54 上加载即失败：1360: (7b) *(u64 *)(r11 -8) = r6 — R11 is invalid（flow.rs:486，conn_save 调用点）。此前内核级验收走 QEMU 7.2.8 矩阵，未覆盖宿主内核加载。

根因：e87ea69（eBPF 余项批次）把 conn_save 扩到 7 个参数。BPF-to-BPF 调用只有 5 个寄存器参数，第 6 个起走栈传参；本工具链（nightly 1.101 + bpf-linker 0.11.1）为栈参数生成 R11 伪寄存器访问且未消除（对象内共 4 处，仅此一调用），6.18 验证器直接拒载。

修复：参数打包为 4 个——conn_save(key, mark, meta, generation)，其中 meta = outbound | must<<8 | l4proto<<16 | slot_enc<<24；#[inline(never)] 独立子程序帧保留（combined stack 约束不变）。修复后对象 R11 = 0，lab.sh verify 宿主全绿：12/12（proxy / direct / block / host-wan / reload / rebind / status / fault-reload / l3-attach / l3 / xdp / fault-kill）。

该修复尚未提交（工作区改动 sodama/ebpf-rs/src/flow.rs），建议随本轮报告一并入库。修复不改变数据面语义（值等价搬运），对性能影响在噪声内（vless 16 589 与历史同级）。

8.2 实验室 offload 口径（新 lab 使标准路径吞吐减半）

现象：默认 lab 拓扑下 sodama VLESS 只有 8.3–9.2 Gbps（CPU 140–190 ms），对照历史 16.9 G。perf 剖面：csum_partial 13.9% / memcpy_orig 11.5% / memset_orig 6.8% / skb_segment 1.6%（均为"软件校验和+软件分段"特征）。

定位：47c603a（今日 L3 收口批次）引入 lab/net_offload.py，up() 中无条件对 dae0/dae0peer（控制面对，代理流量的用户态交接通道）关闭 offload——本意是修 L3 隧道内层校验（ipip 场景），但代理路径的数据面恰经这对 netkit 进出用户态，GSO/校验和卸载被一并关闭。

A/B 实证：同一构建、同一命令，加 SKIP_NET_OFFLOAD=1（lab 内置开关）后 sodama VLESS = 17 237 / 17 315 Mbps（+103%）。M1 时代 lab 无任何 offload 动作（已核对 4739410 的 lab.sh），故历史数字均为默认 offload 口径。

处置：本轮全部压测统一 SKIP_NET_OFFLOAD=1（与该 L3 修正不冲突：L3 用例不参与本口径）；建议后续把 dae0/dae0peer 的 offload 关闭动作收进 L3 用例内部（用例前关、后恢复），或在 lab 文档中把"性能轮必须 SKIP_NET_OFFLOAD=1"写成硬口径。

解读与修复方向：ss 是"全 AEAD 每字节"的 codec，迁入 reactor 后每连接的双向加密在单一 worker 上串行交错；旧线程泵路径（每连接独立泵线程，可跨核并行）+ 每字节拷贝的调度更有利。表现为：快轮可达 9 G（说明算力足够）但慢轮增多（调度/流水线化不足），且 CPU 总量反而不高（520 ms vs 历史 590 ms vs wall 更长的"stall"形态）。建议：① 复核 reactor codec 的 rx/tx 交错策略（同会话两方向分派到不同 worker 或显式流水线）；② 或为"每字节重加密类 codec"保留线程泵回退路径；③ 在 lab 增加 ss 吞吐门禁（本轮数据已可作基线）。

8.4 UDP 回程全灭回归（提交级二分：e5db7fd）

现象：ss UDP 代理路径在 ≥10 000 pps 时回程全灭（上行 100% 转发、客户端 recv≈0）；≤5 000 pps 正常。

探针内容20k pps ×2 轮结果判定
08d14e6A2 前最后代码提交recv=4000 / 4000（零丢包）通过
26a0411A2 批次 4recv=4000 / 4000（零丢包）通过
e5db7fdA2 批次 5（UDP GSO 引入）recv=1 / 0（全灭）失败

机制（代码级证据）：loader/src/main.rs 的 udp_gso_enable()（8723 行）用 setsockopt(SOL_UDP, UDP_SEGMENT, 1) 做"能力探测"并留下副作用——该回复 socket 的 gso_size=1；随后 send_gso_udp() 在 hdr.msg_controllen 仍为 0 时调用 CMSG_FIRSTHDR(&hdr)（glibc 要求 msg_controllen ≥ sizeof(cmsghdr)）→ 恒返回 NULL → 提前 Ok(false)，GSO 发送从未真正发生、回落 sendmmsg。于是：首次"同目的等长 ≥2 报"批次触发 enable（污染 socket），此后该 socket 上一切回复发送都被内核按 gso_size=1 处理/拒绝 → 回程全灭。

关键实证：① 20k pps 失败后，同一会话下 2k pps 重试也全灭（新进程新会话则 2k pps 正常）——污染持久于 socket；② udp_nat.sessions_proxied 计数表明上行全量转发；③ 状态面 gso_sends 不增长（发送未发生）。

修复方向：① 在 CMSG_FIRSTHDR 前先设 msg_controllen（或直接手写 cmsghdr，不依赖 CMSG_FIRSTHDR）；② 探测不得留下 gso_size=1 副作用（例如探测后用 UDP_SEGMENT=0 复位，或仅通过首次真实 GSO sendmsg 的 EINVAL 反馈回落）；③ 增加 UDP 高 pps（≥10k）的门禁用例——本轮数据表明既有 verify/cap 用例未覆盖该速率窗。

11.1 订阅与节点特性（为什么需要适配）

  • 订阅（base64）解码为 20 个 VLESS+WS+TLS 节点：host/sni=sub3.example.com、fp=chrome、path=/proxyip=<8 个 IP>，端口 ∈ {2053, 2083, 2087, 2096, 8443}，20 个不同 CF 边缘 IP。链路 RTT ≈ 180–190 ms。
  • worker 只接受域名目标：以 IP 为目的地的请求被直接关连接（上一轮实测，WS Close 帧 \x88\x00）。因此三方对比实现（sodama/dae/sing-box；v2ray 仅作参考客户端）都必须「嗅探 SNI/Host → 域名拨号」——这本身是各家能力的真实对照点。sodama 用 --dial-mode domain+（严格档 domain 对未知域名首连按 IP 拨出，会被 worker 拒），dae 用 dial_mode: domain+、sniffing_timeout: 500ms，日志证据见数据目录 evidence.txt。
  • sing-box 1.14 无等价能力：sniff action 在 1.14 只剩 sniffer/timeout；1.11 起的 sniff_override_destination 仅为遗留 no-op（schema:"omit"，且 RuleActionSniff.OverrideDestination 在构造时从不被赋值），嗅探结果不会回写拨号目标（源码事实与逐项实测见 evidence.txt §2）。本轮改用 route action 的 override_address（badoption.Addr 支持域名）静态指定目标域名，并保留 sniff 规则以对齐嗅探工作量。
  • 固定后端：real.sh prepare 将节点固定到一个 TCP 可连的 CF 边缘（203.0.113.123:2053），三方共用；出口取路径参数里实测健康的单一 proxyip（见 11.4）。

读数：① 三方代理吞吐相当（18.6–19.3 Mbps，中位差 ≤4%）——节点出口带宽（≈2.3–2.5 MB/s）是共同上限，直连基线 36 Mbps 说明瓶颈既不在本机也不在本地网络；② 进程口径（/proc/<pid>/task/*/schedstat，ns 级）sodama 比 dae 低 31%、比 sing-box 低 28%（每 GB）；③ 内核侧口径（/proc/stat 的 system+irq+softirq，逐轮扣除前置 1 s 空闲基线）给出 sodama ≈ dae 的 0.48×、sing-box 的 0.39×（点估计），该口径 CI 较宽（与 dae 略有重叠），其用途是给 sodama 的 eBPF 工作量一个上界估计；两个口径排序一致。

为什么可以这样比：sodama 的转发在 eBPF 里完成，进程口径天然漏计其内核工作量——这正是内核侧口径存在的理由。即使把内核侧全部计入，sodama 每 GB 总 CPU（12.6k ms）仍显著低于 dae（24.4k）与 sing-box（28.8k）；同时该值与本轮无代理直连基线（13.2k ms/GB，跑在 2 倍速率上）同量级，说明该负载下（≈19 Mbps）代理引入的额外 CPU 成本可忽略。

交叉验证：同夜更早一次 17 轮（出口池未固定、条件更差；sing-box 有 2 轮短传输未剔除）进程口径为 sodama 2 947 / dae 4 465 / sing-box 4 374 ms/GB，排序与量级一致（real-final.tsv）。

11.4 节点侧抖动与处置（复现要点）

  • 出口池抖动：默认 8 出口路径下，v2ray 参考客户端 20 轮中 17 轮传输被截断（SSL routines::unexpected eof while reading，体积 16 KB–1.5 MB，耗时 2.3–3.0 s）；换 CF 边缘 IP 无效（多边缘均 1–2/4 失败）→ 问题在出口池。逐出口单测后固定健康出口（203.0.113.68，2.41/2.42 MB/s），残余失败率降至 ~25%（节点侧固有）。
  • 脚本处置：本轮给 real.sh 增加 ① 短传输判定 TARGET_EXPECT_BYTES（curl 对截断的 TLS 会话仍可能返回 200）、② 单轮最多 ROUND_ATTEMPTS 次重试，两者否则会把「截断轮」计成低吞吐低 CPU 的伪样本（本轮第一次 17 轮就因此丢掉 dae/singbox 的数据）。
  • 其他坑：/tmp 为 sticky + world-writable，宿主 fs.protected_regular=2 会拒绝 root 以 O_CREAT 打开他人拥有的常规文件——生成配置前先 rm -f（已入 gen_singbox_cfg/gen_dae_cfg）；dae 数据重建会清掉 dae0，real.sh 已有重建分支。
