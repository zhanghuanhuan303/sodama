sodama · VLESS 性能实测与优化提案

同机四方对拍（sodama / dae v2.1.1 / sing-box 1.14.2 / v2ray 5.52.0）· 明文与 TLS 两种 VLESS 形态 · 5 轮中位数 · 2026-10-04
数据口径 5 轮中位 夹具 全双工 echo · 环回上限 ≈25 Gbps 上游 sing-box VLESS server（四方共用） 路径 client ns → 网关 → WAN ns perf -g 采样热点 结论 VLESS+TLS 综合第一梯队

三句话结论：① VLESS+TLS 形态下 sodama 已进入第一梯队（吞吐 ≈ sing-box 的 97%、CPU 更低、延迟最低、内存只有对手 40–50%）； ② VLESS 明文的差距（12.2 G vs sing-box 16.6 G、380 ms vs 80 ms）几乎全部来自 零拷贝缺失——数据面 65% 的 CPU 花在 rep_movs + 建页； ③ 提案按「先零拷贝、再 TLS 降本、后规模与生态」推进：第一阶段完成后预计明文 ≥16 G / CPU ≤150 ms，TLS ≥13 G，同时补上 Vision-over-TLS 以对齐主流节点。

02 · 方法与环境

同一台机器、不同 netns；四方共用同一个 WAN ns 内 sing-box VLESS 服务端（明文 :8543 / 自签 TLS :8544），目标 1.1.1.1:8080 由服务端本地拨达。负载：每轮 48 MB × 4 流全双工回显 + 500 次 RTT；预热 1 轮、取 5 轮中位数；吞吐对比关闭半关闭（语义差异另有专项）。

sodama_client ns ──landae── [网关: eBPF / tproxy] ──wan── sodama_wan ns
                                       ├─ bench_io :9999  (direct 目标)
                                       ├─ bench_io :8080  (代理目标)
                                       └─ sing-box :8543  (VLESS 明文) / :8544 (VLESS+TLS)
  • 夹具为全双工 ring echo（BENCH_RING_MB=128）；4×48 MB 环回上限 ≈ 24.5–25.7 Gbps，因此 direct 行是夹具受限的下界，不用于比较实现上限；
  • CPU = 网关进程 utime+stime 增量（不含上游与夹具进程）；RSS/线程取负载期样本；
  • sodama：eBPF 重定向 + 用户态 relay；dae：eBPF；sing-box/v2ray：nftables tproxy（各官方推荐部署）；
  • 版本：sodama f10298c+（含 P33.2 性能线）· dae v2.1.1 官方 release · sing-box 1.14.2（pacman）· v2ray 5.52.0（pacman）。

复现：sudo PROXY_PROTO=vless ROUNDS=5 lab/perf/run.sh all（TLS 用 PROXY_PROTO=vless-tls）；并发扩展 lab/perf/scaling.sh。

09 · 分析

  1. VLESS+TLS 是 sodama 当前最强的代理形态：11.6 G / 46 µs / 420 ms / 29.8 MB，综合优于 dae 与 sing-box，且延迟、内存、线程全面领先；
  2. 与 sing-box 的明文差距 = 零拷贝差距：sing-box 80 ms 的 CPU 说明它走的是 splice 类零拷贝；sodama 46.8% + 18.8% 的搬运/建页成本与之对应。计划用 splice()（socket↔socket 经 pipe）把该成本清零；
  3. TLS 形态的下一档收益来自「少一次拷贝」：libc memcpy 7.6% + 建页 9.7% 是 rustls 记录层与内核 skb 的搬运开销；缓冲池化 + 记录层就地读写可省一半，kTLS 是后续的激进选项；
  4. 加密算法选择重排：本机 AES-NI 下 AES-256-GCM ≫ chacha20-poly1305 AVX2（14.9% vs 41%）；ss 节点允许时优先协商 aes-256-gcm，或直接以 VLESS+TLS 为主链路；
  5. 规模模型是长板中的短板：122 线程/64 连接、175 KB/连接、连接建立依赖线程 spawn；事件驱动/worker 池是万级连接的前提；
  6. 生态缺口：主流「VLESS+TLS+Vision」组合中 sodama 的 vision 仅在 REALITY 路径实现；不补齐会在真实节点上退化为「VLESS+TLS 无 vision」，流量特征与性能均非最优。

10 · 优化提案（按数据排序）

P0
零拷贝数据面（splice socket↔socket） — 对应 VLESS 明文/relay 路径的头号成本
现状拷贝 46.8% + 建页 18.8% ≈ 65% CPU；明文 12.2 G / 380 ms，落后 sing-box 26%（16.6 G / 80 ms）
目标明文 ≥16 Gbps、CPU ≤150 ms（对齐 sing-box 档位）；relay 路径同步受益（15→22 G）
做法每方向 splice(client→pipe) + splice(pipe→upstream)，非阻塞 + epoll；F_SETPIPE_SZ 调大；不可 splice 时回退现泵；保留计数与降级路径
验证scaling.sh vless 8×64 MB：吞吐/CPU 曲线；perf 中 rep_movs/clear_page 占比应下降 ≥40%
P0
VLESS+TLS 降本：记录层少拷贝 + 缓冲池化
现状拷贝 27.5% + AES-NI 14.9% + libc memcpy 7.6% + 建页 9.7%；8 流饱和 11.3 G / CPU 1 450 ms（129 ms·Gbps⁻¹）
目标TLS 8 流 ≥13 G、CPU ≤1 000 ms；4 流 ≥12.5 G
做法① 泵缓冲/记录层缓冲每连接复用（零热路径分配）；② rustls 读写走 ReadBuf/vectored，减少一次明文↔记录拷贝；③ 评估 kTLS（rustls 导出流量密钥 + setsockopt(TLS_TX/RX)）把 AES-GCM 与拷贝一并下沉内核；④ TLS 会话/票据复用降低每连接握手成本
验证perf 热点搬家（libc memcpy ≤3%）；scaling.sh TLS 曲线；与 P0 的 kTLS 对照
P0
Vision-over-TLS（对齐主流组合）+ ws/wss 变体
现状xtls-rprx-vision 仅在 REALITY 分支生效；真实订阅中「VLESS+TLS+Vision」占主流
目标vless://…?security=tls&flow=xtls-rprx-vision 可用；与 sing-box/xray 节点 e2e 通过
做法把 vision 读写半（VisionReader/Writer）接到 tls 分支；补齐 padding/长度语义与半关闭；lab 用 sing-box 服务端 vision flow 对拍 + 真机订阅验证
验证lab 四路（sodama/dae/sing-box/xray）512 KB 逐字节；真实节点 66/66
P1
连接规模：worker 池替代每连接线程
现状64 并发 = 123 线程 / +11 MB；每连接 spawn/join 成本计入 RTT 与内存
目标线程数 O(核数)；4096→10000 连接吞吐/内存平稳；小包 p99 改善
做法epoll 事件循环 + 连接状态表（含半关闭/janitor/offload 看门狗统一计时）；保持 eBPF accept 语义不变
验证新增连接压力基准（新建/s、512/4096 并发 RSS/吞吐）
P1
加密策略重排：AES-GCM 优先 & ss 路径零分配
现状ss 路径 chacha+poly 占 41% CPU；同机 AES-NI GCM 仅 14.9%
目标ss 节点支持时优先 aes-256-gcm；ss writer/reader 去逐块 Vec 分配与多余 syscall（lb+payload 合并写、预读解析）
验证ss 8 流 CPU ≤460 ms（对齐 dae）；方法对照表
P2
零散纯开销清理（低成本、确定收益）
  • bpf_printk 热路径门控（当前 0.3–0.5%，高 PPS 放大；改 debug map 开关）；
  • UDP 批量 recvmmsg/sendmmsg + per-CPU 会话表（G1 缺口，需补同口径对拍）；
  • 半关闭/关闭路径的统一收敛（SIGTERM 1–3 s → ≤500 ms）。

11 · 风险与边界

  • 夹具边界：direct 行受环回 ≈25 Gbps 限制（客户端 pattern 校验 CPU），不代表 eBPF 上限（64×1 MB 口径 35.2 G 为参考）；绝对吞吐不能外推到真实公网；
  • 上游同源：四方共用 sing-box VLESS 服务端，与 ss 轮的 ssserver 一样，高并发下可能成为共同天花板；横向对比成立；
  • splice 与 tproxy 的兼容性：目标 socket 为 tproxy 绑定的本地 socket，splice 对 socket↔socket 经 pipe 可行，但需实测穿越 eBPF 重定向后的语义（半关闭、RST、sockmap offload 的优先级）；
  • kTLS：需要从 rustls 导出流量密钥，rustls 未公开该接口，属于「需要自实现 TLS 或切换后端」的激进选项，先做评估 spike；
  • Vision 语义：需与 sing-box/xray 行为对拍（padding、块大小、直通标记），否则可能被服务端判为异常流；
  • 测量噪声：同机 16 线程、veth 环境，round-to-round ±5–10%；本提案所有结论基于 5 轮中位数与跨路径一致性。
