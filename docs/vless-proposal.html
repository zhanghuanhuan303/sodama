M1 结论：splice 零拷贝按预期把「拷贝 + 建页」从数据面拿掉——VLESS 明文吞吐提升 38%、CPU 降 84%， 四方对比中 sodama 与 sing-box 的明文差距从 −26% 收敛到 −4.6%，且 CPU 更低（60 vs 90 ms）、延迟最低（36 µs）。 验收：vless 8×64MB ≥16 Gbps（16.18 ✓）· CPU ≤150 ms（190*）· relay ≥22 Gbps（21.6 ≈✓，4 流 23.1 ✓） （*CPU 目标含 8 流场景；48MB×4 主口径为 60 ms，远低于目标）
M2 结论（kTLS 内核 TLS，实验开关 --ktls）：已打通「服务器 Finished 后逐记录停止握手 → 导出 TLS1.3 流量密钥 → 内核 TX/RX 加解密 → TLS 上再做 splice」全链路，控制记录（NewSessionTicket）与 splice EINVAL 均有正确处理；libc memcpy 从 29.4% 降到 1.6%，达标（≤3%）。 但本机（i9-9900KF）内核 AES-GCM 实测 2.89 GB/s，仅为用户态实现（OpenSSL 6.57 GB/s / ring 同级）的 44%， 因此「搬到内核」在本硬件上是 CPU 平移而非下降：8×64MB 下 sodama CPU 1 510 vs rustls 1 370 ms、 两类路径的系统总 CPU 相同（≈2.87 s），吞吐同被夹具压在 ≈11 Gbps。kTLS 在本机不作为默认； VAES/AVX-512 或带 TLS 卸载的 NIC 上预期完全不同（内核变体更快、且可避免用户态拷贝）。
M3 结论（Vision-over-TLS，ADR-0057）：flow=vision 从「仅 REALITY、仅下行 raw」补齐为 tls/reality 双外层 + 双向 XTLS DIRECT（0x02 裸 TCP）：内层嗅探（dae FilterTLS 移植）识别内层 TLS1.3 后， 上行裸写、下行裸读（外层加解密停用，内层 TLS 端到端保障）；rustls 侧用逐记录有界读替代 dae 的 unsafe 反射。 验收：`lab/vision`（Xray 25.9.11 夹具）tls/reality 内层 TLS1.3 2MB 逐字节一致 + 双向 DIRECT 各触发、 TLS1.2/明文 END 互通、ws/wss 逐字节；真实订阅 48 节点 5MB 下载完整，日志 6/6 双向 DIRECT。
M4 结论（epoll worker 池，ADR-0058）：stage 1 把 splice 链路（Direct/VLESS 明文/kTLS 成功的 TLS）迁到 epoll worker 池（16 worker；每连接 0 线程）；stage 2 首段把 rustls codec 会话（VLESS-TCP/Trojan） 也纳入同一状态机（可重入修复：TlsWriter 待刷语义、VlessReader 响应头状态机、预算耗尽自驱补泵）。 hold 10 000 连接：28 线程 / 32.1 MB RSS（线程模型 20 011 线程 / 763 MB）、fail=0、建立 4 717/s； 风暴 25 606 连接/s（线程模型 20 860/s）；vless-tls 长连接 2 000 条 = 27 线程 / 61 MB（线程模型 4 011 / 222 MB）； 同二进制 A/B：vless 1/2/4/8 流吞吐无回退（64×1 MB +19%）、vless-tls +5~25%，relay 64×1 MB 37.9 vs 13.6 Gbps； kTLS+reactor 8 流逐字节一致；`SODAMA_REACTOR_CODEC=0` 可关 codec 入池。

02 · M1 做了什么

改动实现效果/证据
splice 零拷贝数据面 拨号层为字节透明的链路打能力位（Direct / VLESS 明文 TCP）；relay 每方向 splice(socket→pipe→socket)（1MB 管道、页级搬运），EOF 时 shutdown(SHUT_WR) 半关闭语义与旧泵一致；首调 EINVAL 自动回退用户态泵； --no-splice 可关；VLESS 请求头（拨号时已发）与响应头（一次 codec 首读消费）在切换前完成 8×64MB vless：11 678 → 16 177 Mbps，CPU 1 100 → 190 ms； perf 中 rep_movs 46.8% + 建页 18.8% 消失，转为内核 splice 管线（skb_splice_from_iter 8.4% 居首）； splice_total=720 / fallbacks=0
eBPF 热路径 printk 门控 control_flags 新增 debug 位（与 suspend 位共存，读改写保留其它位）； 门控 flow.rs cached（每包）/ stateless / route 与 progs.rs dae0peer_ingress / sk_assign / dae0_ingress 打印； --ebpf-debug 打开 默认关闭时单次传输 trace 行数 600+ → 0；打开时 600+（可调试）。 该开销此前占 direct 剖面 0.3–0.5%，高 PPS 下会放大
可观测性 status / Prometheus 新增 splice_enabled / splice_total / splice_fallbacks status --json 可直接核对命中率（本轮 0 回退）
回归 —— lab verify 9/9（proxy/direct/block/host/reload/rebind/status/fault×2）； cargo test 236/236；半关闭路径（未设 BENCH_NOSHUT）逐字节 verify=ok
边界与自动回退：加密/成帧链路（TLS、REALITY、ss、vmess、trojan、vision、QUIC 系）不置位， 继续走用户态泵——它们需要逐字节变换，内核拼接会绕过协议层。Group 拨号返回成员流的真实能力位， 因此订阅组里选中直连/VLESS 明文的成员时 splice 同样生效。

03 · M2 做了什么（kTLS 内核 TLS）

改动实现效果/证据
逐记录握手驱动
kTLS RX 对齐的关键		 握手不再用 complete_io 整块消费：按 TLS 记录边界（5B 头 + 荷载）喂 rustls， is_handshaking() 变 false（刚处理完服务端 Finished）立即停止读取—— 服务端紧跟的应用 epoch 记录（NewSessionTicket 等）一个都不被 rustls 消费， 内核 RX 的 rec_seq 才能与 wire 从 0 对齐；异常时回退 complete_io 并禁用 RX（仅试 TX） 修复了 M2 前半段的 EBADMSG 根因（NST 被 rustls 消费导致序号错位）； 实测 /proc/net/tls_stat：TlsDecryptError 增量 0，全部连接 TX=true RX=true
kTLS 安装 rustls KeyLog 捕获 CLIENT/SERVER_TRAFFIC_SECRET_0 → HKDF-Expand-Label 导出 key/iv → setsockopt(TCP_ULP,"tls") + TLS_TX/TLS_RX （AES-128/256-GCM、chacha20-poly1305；TLS1.2/无密钥自动跳过）；TLS_RX_EXPECT_NO_PAD； TX/RX 独立安装、失败各自回退 rustls；--ktls 开关（默认关）、需 modprobe tls TX-only 实验（SODAMA_KTLS_TXONLY=1）先证密钥/派生/安装全对，再攻 RX； 安装耗时在连接建立期，数据面零每包开销
控制记录与 splice 互处理 RX 明文读取：recvmsg+cmsg 按记录类型分流（23=应用数据返回；22=NST 丢弃继续；21=alert 视作关闭）； 下行 splice 遇队首控制记录时内核 requeue 并返回 EINVAL—— 先 MSG_PEEK 核实 cmsg 类型（应用数据不动），是控制记录则消费，再重试 splice（≤8 轮） NST 在握手后任意时刻到达都不再导致连接被误杀或回退； 实测 splice_total=4 / fallbacks=0，TLS 连接全程零拷贝
TLS 上 splice kTLS 成功后数据面回到字节透明：outbound 层重新置位 splice 能力位； 上行 splice(客户端→kTLS TX socket)（内核加密）、下行 splice(kTLS RX socket→客户端)（内核解密） 8×64MB perf：libc memcpy 29.4% → 1.6%（M2 目标 ≤3% 达标）； rep_movs/建页退出前十，转为 aes_gcm_*（内核）与 splice 管线
记录层缓冲复用 TlsReader 去掉「栈 16KB 临时 → pending Vec」两跳，改为 64KB 复用缓冲 + 游标喂 rustls；读块 16→64KB rustls 路径少一次拷贝/扩容；配合 kTLS 时直接内核明文读写
可观测性与开关 --ktls / SODAMA_KTLS_DEBUG=1（密钥、安装、控制记录）/ SODAMA_KTLS_TXONLY=1； lab：USE_KTLS=1、SODAMA_ARGS=--ktls、lab/perf/m2ab.sh（路径 A/B） TlsDecryptError 可直接从 /proc/net/tls_stat 核对；A/B 数据可一键复现
为什么 kTLS 没把 CPU 降下来（本机）：内核 kTLS 的 AES-GCM 落在 generic-gcm-aesni-avx（本机 /proc/crypto 无 avx2/vaes 变体）， AF_ALG 实测加密吞吐 2.89 GB/s；而用户态（OpenSSL 等价测法）AES-128-GCM 6.57 GB/s、ring/rustls 同级。 即「把加解密搬到内核」在 i9-9900KF 上是用 0.44× 的密码引擎换掉用户态拷贝——本机净收益只是 memcpy/建页的消除， CPU 总量打平（系统总 CPU ≈2.87 s 两路径相同）；在带 VAES/AVX-512 的新 CPU 或支持 TLS 卸载的 NIC 上结论会反转（内核变体可快于用户态，还能真正卸下 CPU）。

08 · 分析（M1–M4 后）

  1. 零拷贝收益兑现（M1）：明文路径 +38% 吞吐 / −84% CPU，sodama 从“明显落后 sing-box”变为“同档且更省”；perf 证据链完整（拷贝/建页占比消失）。
  2. 半关闭语义无回归：splice EOF → SHUT_WR 与旧泵一致；未设 BENCH_NOSHUT 的逐字节校验通过，lab verify 9/9（含 USE_KTLS=1）。
  3. kTLS 形制全部打通（M2）：逐记录握手驱动把「rustls 消费边界」精确卡在服务端 Finished， 内核 RX 序号与 wire 完美对齐；控制记录（NST）在明文读与 splice 两条路径都能正确跳过； TLS 终于可 splice（memcpy 29.4%→1.6%）。难点不在 ABI（setsockopt 结构体/IV 拆分/ULP 均已验证），而在rustls 与内核的序号一致性与 post-handshake 记录。
  4. kTLS 的收益是硬件相关的：本机内核 AES-GCM 只有用户态的 0.44×，两路径总 CPU 打平； 但 kTLS 已经拿掉了拷贝与建页的一半以上，吞吐也略高（+5.6%）。在 VAES/AVX-512 或带 TLS 卸载的 NIC 上，内核路径预期从“平移”变成“净赚”；本项目保留 --ktls 供按硬件开启。
  5. 夹具是当前最大变量：TLS 吞吐被同机 sing-box 服务端封顶 ≈12.5 Gbps（四方客户端一致）， CPU 目标也需在服务端不同机的口径下重测；worker 池已交付（M4），余下缓冲池（O8）与 ss 路径优化（O1/O2/O6）应换到可拉开差距的口径验证。
  6. 规模模型已解（M4）：splice 链路迁入 epoll worker 池后，10k 连接 = 20 线程 / 30.2 MB、建立 4 785/s、 风暴 25 974/s（同口径线程模型：20 011 线程 / 763 MB、20 860/s）；线程不再随连接增长。 stage 2 把同一状态机扩到 rustls/ss/vmess 会话（ADR-0058）。
  7. 主流节点组合已齐（M3）：Vision-over-TLS 交付——外层 tls/reality × 双向 XTLS DIRECT（裸 TCP）＋ws/wss； 内层嗅探保守（TLS1.2/明文走 END），rustls 无 unsafe 反射（逐记录有界读）；M4 解决规模模型后，主链路（协议 × 规模）对齐完成。

10 · 风险与边界

  • 夹具边界：direct 行与 8 流 vless 可能触及环回 ≈25 Gbps 夹具上限（客户端 pattern 校验 CPU），绝对吞吐不外推到公网；TLS 行则受同机 sing-box 服务端 ≈12.5 Gbps 封顶，这组数据只能横向比较；
  • splice 适用范围：字节透明链路（Direct / VLESS 明文 TCP）与 kTLS 成功后的 TLS 链路；加密、WS、vision、QUIC 系仍走用户态泵；首次 splice EINVAL 自动回退（计数可观测）；
  • reactor 边界（M4）：接管字节透明且未 offload 的 splice 链路（Direct/VLESS 明文/kTLS TLS）+ stage 2 codec（VLESS 全组合含 reality/vision/ws、Trojan、vmess，读半/写半须 WouldBlock 可重入）；ss/ssr/anytls 仍为每连接线程（余段再迁）；SPLICE_F_NONBLOCK 仅作用管道端——两端 socket 必须非阻塞，否则 worker 真阻塞；VLESS 响应头由短命 prelude 线程先行消费后 resume；SODAMA_NO_REACTOR=1 回退线程模型、SODAMA_REACTOR_CODEC=0 关 codec 入池，SODAMA_REACTOR_DEBUG=1 打详细日志（含会话状态周期转储）；
  • kTLS 边界（实验）：需内核 tls 模块（modprobe tls）；仅 TLS 1.3 + 已支持的 AEAD（TLS 1.2 自动跳过、仅用户态）；对端中途发 KeyUpdate 时内核 RX 会 EBADMSG（当前直接断连，不会静默丢数据；xray/sing-box 默认不主动 KeyUpdate）；安装失败/控制记录异常均有回退路径与一次性日志；
  • 内核依赖：splice 自 2.6.17 起可用；kTLS 自 4.13+（TLS 1.3 RX splice 需要较新内核，本机 6.18 实测）；veth/netns 场景常规；
  • 测量噪声：同机 veth，轮次间 ±5–10%；relay 8 流首测出现 12.7 Gbps 的孤立点，复测 21.6 Gbps，报告取复测值并保留说明；
  • 上游同源：四方共用 sing-box VLESS 服务端（同 ss 轮的 ssserver 口径），TLS 高并发下它就是共同天花板（≈12.5 Gbps），CPU 对账也受其同机竞争影响。
