§1缘起 · 三个研究问题与一次可行性押注

重写一个已经能用的内核，只有在它能回答几个可证伪的问题时才值得做。否则那只是在制造一个新的、更年轻的 bug 集合。

上游 dae 的架构本身是优雅的：把分流决策下沉到 eBPF，让内核直接转发未命中规则的数据包，用户态只处理需要解密的那部分流量。它在 x86 软路由上跑得很好。真正让人坐不住的是用户态内存的连接数曲线——实测中，dae 的用户态 RSS 随连接数近似线性增长，20 000 连接时达到 1 662 MB，即每连接约 82.7 KB 的净增。3在 4 GB 内存的软路由上，这条直线就是可用性的天花板。

Go 的 GC、goroutine 栈与每连接对象开销，是这条直线的来源。它不是一个 bug，而是运行时的成本结构。Rust 提供了另一种成本结构：没有 GC、没有协程栈的隐式增长、内存归还可以显式控制。于是有了三个可以被证伪的问题：

  1. 数据面语言。eBPF 程序能否完全用 Rust（aya-ebpf + BTF/CO-RE）重写，并保留上游全部分流语义？上游 4 403 行 C 的 eBPF 程序族（23 程序 / 24 map）。约束是：不能用 libbpf 的便利宏，map 定义要走 BTF，内核态没有 std，panic 即丢包。
  2. 语义保真。规则编译器（geoip/geosite 展开、LPM 位图、domain 索引）能否与 Go 版逐字节对拍？如果做不到，所谓「重写」就只是「另写了一个相似的软件」。
  3. 性能不回退。去掉 GC 之后，吞吐、延迟、CPU、内存四个维度能否同时不劣于上游？

三个问题的答案都是肯定的，但它们的证明方式各不相同：第一个靠代码退役（C 目录被删除，eBPF 对象整体改由 nightly Rust 工具链产出）8；第二个靠 5 组规则编译产物的逐字节比对；第三个靠一套受控实验——本图集 §4 的全部数据。

研究方法上的一条前置决定：先做内核攻坚，再做生态接入，最后逐步替换。顺序不能颠倒。内核（eBPF 数据面 + 分流语义）是唯一无法用「换个库」绕过的部分；协议栈可以按家族逐个补齐；订阅生态是最后才需要面对的长尾。事实证明这个顺序是对的：真机接入订阅时暴露的三个问题（组 UDP 拨号缺陷、订阅正文截断、procd fd 硬限）全都不在协议栈里，而在数据面与控制面的接缝上。

§3架构总览 · 内核态与用户态的四层分解

3.1 · 内核态数据面

22 个 eBPF 程序（12×TC：6 角色 × L2/L3，含单臂 dual-role 变体 + 1 个 sk_skb offload + 6×cgroup + 1×fentry + 1×kprobe + 1×xdp）与 22 个 BTF map，约 2.1k 行 Rust（2026-10-16 数据面对标批次后，ADR-0065）。上游是 23 个程序 / 24 map / 4 403 行 C——本批次后 sodama 数量上趋于对齐，但组合方式不同：上游 13 个 TC 变体含大量 L2/桥接组合，sodama 用 6 角色 × L2/L3 的 12 个 TC 程序覆盖主形态（余 lan_egress 角色）。生命周期用 TCX 而非传统 cls_bpf：挂钩随进程退出自动摘除，回滚天然安全——这条设计在后续的生产事故中直接救了场（见 §6 第 1 则）。

3.2 · 用户态：从「每连接一线程」到 Reactor 池

最初的转发实现是每连接 1–2 个 OS 线程的泵模型。它在 64 并发时工作良好，在 10 000 并发时是灾难：20 012 个线程、527.4 MB。M4 引入 epoll worker 池（默认 16 worker，上限按核数）后，同一负载降到 29 线程 / 34.8 MB。7关键在于 codec 会话也被搬进了 worker 内：每条 offload 连接占用 0 个线程。

转发原语经过三档对照后定为：默认 splice（socket→pipe→socket 零拷贝）；fd 使用率 ≥80% 时新会话自动降级为用户态 copy pump（用吞吐换可用性，降级计数可观测）；低时延场景无回退。splice 把 VLESS 明文路径从 12 225 提到 16 926 Mbps、进程 CPU 从 380 ms 降到 60 ms。--no-splice 可关。io_uring 做过交叉配对 A/B（中位 8.18 vs 8.11 GB/s），结论是不引入——差异在噪声内，而复杂度是真实的。

3.3 · 控制面：配置文件是唯一事实来源

全局参数、订阅列表、节点、组、DNS、分流规则、规则集 URL、用户自定义名单——全部收敛进 config.dae 一份文件，运行时没有任何「只能在命令行给」的行为参数。改动经 inotify 毫秒级热驱动，无需重启、无需发信号。9配置目录默认 ~/.config/sodama；没有 home 目录的软路由环境自动落到 /etc/sodama。订阅列表按声明顺序回退，语义类似 pacman 源：首个有活节点的源生效，改顺序即切换。分流规则集独立成文件，支持标准格式并可从 URL 自动更新与缓存，用户也能手动添加「强制代理」或「强制直连」的域名。

3.4 · 可观测面

状态 socket（status / rules / config / maps / metrics / reload / suspend / resume）+ Prometheus 指标 + sysdump/trace + 自研控制台 sodama-panel（axum + Leptos→WASM，单文件 musl，含内核参数可视化与 validate 护栏）。上游 dae 主线没有这一层——它的 daed 是一个独立项目。1

4.2 · 内存四层模型

只报 RSS 是不完整的。我们把内存拆成四层：进程（RSS/线程/fd）→ 内核（Slab / SUnreclaim / sockstat / bpftool map）→ 系统总量 → 每连接，每个点都取同点邻近增量（起压前 1 s vs 连接建立后 1 s），并用「同拓扑不放实现」的对照组扣除夹具自身的开销。3

第三份评审提出的质疑与实测回应。评审推算「splice 需要 pipe，Linux 每 pipe 默认 16 页（64 KB），2 000 连接可能吃掉数百 MB 内核内存」。实测结论是：本项目 F_SETPIPE_SZ = 1 MiB，20 000 连接同一时刻持有 20 000 条 pipe，容量上界达 20 GiB；但 slabinfo 中不存在任何 pipe 命名 cache，整个 hold 的 Slab 总增量 1.17 GiB（含全部 socket 链），远低于容量推算。capacity ≠ resident：pipe 缓冲页按需分配、读空即释放。以容量推算常驻内存在这条内核上不成立。这条口径后来被写进了报告的方法学章节。

5.1 · 三级验收：单测 / lab 专项 / 跨实现逐字节

单元测试（10-06 基线 268 项 → 数据面对标批次后 302 项）只证明函数级行为。真正的信心来自第二级与第三级：lab 专项在 netns 里跑真实拓扑（双拓扑 × 九用例、嗅探 punt 三路径、UDP v6、DoH-h2、ECS 回填与刷新、Vision XTLS 状态机……）；跨实现逐字节则把产物与另一个独立实现对齐——规则编译输出与 Go 版对拍 5/5，Vision 帧层与 Xray 夹具四模式逐字节，TLS 记录层与 Go/quic-go 参考服务端互操作，shadow-tls v1/v2/v3 与 sing-shadowtls 三版交叉。为什么「跨实现」比「自测」重要：自测只能证明自洽，跨实现才能证明正确。一个编码器只要编码与解码互为逆运算，就能通过所有自测，同时和世界上其他所有实现都不兼容。

5.2 · 夹具工程学

三次踩坑把夹具从「辅助工具」提升为「需要被验证的被测对象」：

  • 半双工 echo 会制造假死。最初的夹具是单线程 read→write 回显，在多跳大缓冲管道里会与上游实现形成「互相等窗口」的环形依赖，偶发 60 秒级假死——污染了整轮 ss 数据。修复方式是预分配 ring 的全双工 echo，并在 400 轮混合压测中验证 0 失败。
  • 上游会成为共同天花板。第一轮用 Python 做 ss 上游，GIL 把四条实现全部压平到 2.4 Gbps 以下。换成 shadowsocks-rust 后真实差距才显现。横向对比只有在共同上游足够快时才成立。
  • 夹具自己会占内存。用多线程 echo 做 WAN 侧时，1 万连接即 2 万线程，污染 task_struct 统计、并触发 systemd scope 的 TasksMax 上限——一度被误判为 sodama 的线程问题。改为单线程 epoll 的 echo_server 后消除。

5.3 · 口径纪律（七条）

  1. 对照扣除是近似：实现路径 6 个 socket + pipe、对照路径 2 个 socket，「实现净增」仍含共享链路的一部分；两家同口径可比，不可视为独占值。
  2. 命名 cache 归因覆盖约一半：20 k 点 ΔSlab 1 168.6 MB 中命名 cache ≈579 MB，其余为 SLUB 页账与未命名分配，不强行拆分。
  3. 瞬时采样 ≠ 峰值积分：数值是快照；建连窗口内更接近「活跃」，稳态更接近「after」。
  4. capacity ≠ resident：以 pipe/socket 缓冲容量推算常驻内存不成立，一律以实测为准。
  5. 夹具边界要写进结论：direct 4×48MB 受 ≈24.5 Gbps 限制；TLS 8 流受 ≈12.5 Gbps 限制；单目的 IP 端口空间 ≈5.5 万是并发上限。
  6. 时长要诚实：60 min ≠ 72 h。
  7. 措辞降调：不使用「唯一解 / 遥遥领先 / 顶级」；对外统一定位为 predictable resource consumption。

5.4 · 研究性重写的四条经验

  1. 先内核攻坚。唯一无法用「换个库」绕过的部分必须最先做，否则后面所有工作都建在假设上。
  2. 控制变量优于加功能。一次只改一个环境变量的 A/B（Reactor vs 线程模型）比十次新特性带来的认知增量更大。
  3. 可观测优先于优化。没有 status/metrics/sysdump，那次生产事故只能靠猜；有了它们，问题在几分钟内定位到「某个 map 只增不减」。
  4. 事故驱动加固。三个生产问题（map 泄漏、订阅截断、fd 硬限）全部不在实验室用例的覆盖面上——它们都出现在子系统之间的接缝。这是对「实验室通过 ≠ 生产可用」最直白的一次印证。

§6踩坑档案 · 十二则现场笔记

本节是全篇最不「漂亮」、但复用价值最高的部分。收录标准：这个坑换一个人写同样的东西，有较大概率会再踩一次。没有普适性的笔误与拼写错误不收录。

  1. eBPF map 只增不减 → 半死状态（生产事故）

    软路由连续运行 30 小时后，DNS 与代理全灭，但直连与 DNS 缓存完全正常。定位到 redirect_track 地图被填满 65 536 条，新流在 TC 层被 TC_ACT_SHOT 丢弃——而命中直连规则的流量不查这张表，所以「看起来半死」。

    教训：（1）对照上游 Go 版的 cleanupRedirectTrackMap 补上 5 min TTL 清扫 + 90% 容量告警；（2）任何「只增不减」的内核态数据结构都要在评审时被当作定时炸弹；（3）症状与病因分离（缓存正常掩盖了真实故障面）会显著延长定位时间——可观测面必须能直接回答「map 用了多少」。

  2. UDP 组拨号只看延迟榜前三 take(3) 缺陷

    UDP 会话永远回退直连。原因是组内选成员时对按延迟排序的结果取了前 3 名，而在真实订阅里前列被 anytls / reality 占据——这两类协议设计上不支持 UDP，于是「前 3 名全不支持」就成了必然。

    教训：把 take(3) 改成按序全扫（不支持的免费跳过，真实失败至多重试 3 次）。优化排行榜前先确认筛选条件与能力约束正交——「最快」和「能用」是两个维度。

  3. musl 下 malloc_trim 是空实现

    OpenWrt 用 musl，malloc_trim 不产生任何回收效果（分配器不把空闲页还给内核）。实测 mimalloc 在用户态更省，但 daemon 侧 50+ 线程时反而更高（66–87 MB vs musl 37.8–50 MB）。

    教训：不引入替换分配器。回收策略必须按 libc 分支设计，并在目标平台上复测——「本机 Arch 有效」不等于「路由器上有效」。

  4. 半双工 echo 夹具会制造 60 秒级假死

    详见 §5.2。半双工回显在多跳大缓冲管道中与上游形成环形等待。

    教训：基准夹具必须全双工。当四条实现同时出现某个诡异现象时，先怀疑夹具，再怀疑实现。

  5. iperf3 无法与自研代理联调

    iperf3 需要明文 socket 对端，与加密代理的成帧/握手语义不兼容。

    教训：自研夹具不是「重复造轮子」，而是被测路径可终点化的前提。同理，curl 的某些 URL 会被 CDN 策略掐断（HEAD 返回 200 而 GET 秒断），测大流量要用带 UA 的 URL。

  6. procd 的 fd 硬限把并发卡在约 1 000

    OpenWrt 的 procd 给服务设了硬限，即使以 root 运行也受限。修复方式是启动时同时抬高 soft 与 hard。

    教训：跨平台部署时，init 系统会引入你自己代码里看不到的资源上限。上线前先做一次「上限探测」而不是等它撞上来。

  7. BusyBox 环境差异清单

    无 install 命令、sleep 0.5 可能不支持小数、无 python3、无 /usr/bin/time。

    教训：部署脚本要么用 POSIX 最小集，要么在目标平台上跑一遍 dry-run。GNU 工具链的默认假设是路由器上最常见的一类 hidden dependency。

  8. netns 残留导致重启失败

    sodama-datapath stop 后若立即 start，会报 netns daens 已存在。

    教训：清理动作必须等待内核完成回收，或在启动时做幂等的残留检测与清理。这类问题在自动化脚本里会表现为间歇性失败，极难复现。

  9. 配置文件权限校验挡住正常部署

    loader 要求 /etc/sodama/config.dae 的 mode 满足 mode & 0o037 == 0（即不得对 group/other 可写可执行）。

    教训：安全校验要有可读的错误信息与安装脚本里的对应 chmod，否则它会被当成「程序有 bug」。

  10. 订阅正文被截断 → 静默 0 节点

    拉取订阅时响应被截断，解析出 0 个节点但不报错，结果表现为「网络突然不通」。

    教训：改为硬错误。空结果集是最危险的「成功」，因为它把上游故障伪装成了本地配置问题。

  11. 压测前不清理内存 → 进程被 OOM 杀掉

    跑高并发扫描时，机器可用内存只剩 607 MB（swap 已用 18/19 GB），进程被内核杀掉，一度被误判为「引擎内存问题」。

    教训：先清理再测（停掉 rust-analyzer 释放 10.7 GB + 清 page cache），并把这一步写进脚本前置检查。测量环境的健康度是测量结果的一部分。

  12. 脚本误判会伪造出「测试失败」

    并发扫描期间出现过两类误判：清理时误杀夹具进程、建连超时阈值过紧导致把慢判成失败。

    教训：夹具清理按进程名在 netns 内精确执行；超时阈值可配（SETUP_MAX）。测试框架的假阴性会浪费的时间，往往超过它节省的时间。

72h 测试期间的 CF Worker 额度事故（自建线当日 68k/100k 请求）牽出两个叠加缺陷：traffic_active 把「有长连接」恒判为忙，且探测循环的分片睡眠在正常节奏下也被流量「叫醒」——16 成员实测 3.2 探测/秒，是设计值（0.53/s）的 6 倍。修复（P37/P37b）：状态查询不再算「有人在看」、仅退避态允许提前唤醒、失败源负缓存与定向自愈、订阅拉取前置缓存判定。v1.2 生产回验（2d5h39m）：16 节点 32 次/分、36 节点 68 次/分，恰为设计值（修复前 6× 超速）；订阅 2.2 天 10 次拉取 0 失败。「夜间退避 600s」在恒忙家庭网不适用——判据修正为「无流量窗口退避」。

8.5 · AF-XDP 预研（§15，条件性否决）

对「内核旁路」的一次定向预研结论为条件性否决：软路由 4× Intel I211（igb）未接入 xsk 收包路径（只能走 XDP_SKB 慢路径）、既有实测瓶颈在加密与拷贝（rep_movs 46.8%）而非收包、代理架构需配套用户态 TCP 栈才能兑现收益。重评估判据（10G+ 且驱动支持 ZC 等三条以上）固化于 docs/af-xdp-research.md。

8.6 · 内存安全审计与修复批（§16–§18）

8.7 · 数据面对标批次：L3 · ringbuf 事件 · fentry/kprobe 记账 · XDP（§19，ADR-0065）

对照 dae 的数据面，docs/parity-status.md 域 1 曾列三处缺口（backlog C1/C3/C4：L2/桥接程序族、ringbuf 事件通道、XDP 调研），另加 offload 缺「内核路径真实推送字节」的计量。2026-10-16 的数据面对标批次逐一处理：数据面程序到 22（12×TC + sk_skb offload + 6×cgroup + fentry + kprobe + xdp 计量）、map 到 22（BTF），域 1 覆盖度 ≈65% → ≈85%。决策要点、7 项对 dae 的显式偏离与验收命令见 docs/adr/ADR-0065-l3-link-hdr-ringbuf-events-fentry-accounting-xdp.md，过程记录见 docs/phase2-devlog.md §19。实测边界：宿主无 CAP_BPF，但**内核级验收走了仓库既有 QEMU 内核矩阵**（lab/matrix.sh vm，宿主用户即可）——7.2.8 内核上 verify 12/12 全绿（含 l3-attach/l3/xdp）、fentry skb_send_sock 挂载成功（偏移由运行内核 BTF 解出）、记账 kernel_bytes/reclaimed_bytes 实测增长与释出、L3 端到端过关（ipip 隧道：小连接分流 + 512KB 逐字节回显）；未过/待办：offload 用例的 QEMU 既有抖动（随宿主状态大幅波动，四组对照含基线均失败，待查注册交接竞态）、生产 6.12 回验（devlog §19）。

L3 链路头变体。新增 5 个 *_l3 程序（lan_ingress / wan_egress / wan_ingress / wan_lan_ingress / lan_wan_egress），TC 程序族到 12 个（6 角色 × L2/L3）；挂载选择 --link-hdr auto|l2|l3（默认 auto）按 /sys/class/net/<if>/type 判定（对照 dae linkHdrLen()，control_plane_core_bind.go:61-77）。前向：L3 流送控制面前 bpf_skb_change_head(+14) + bpf_skb_store_bytes 补出以太头；回程：按新 map l3_ifindex_map 命中后不写 MAC、不手工剥头，直接 bpf_redirect 回原接口（L2 头的去除由 redirect 语义完成）。这是对 dae 的显式偏离——dae 的 tproxy_dae0_ingress 对 L3 目标接口的回程包会多留 14 B 以太头；而手工 adjust_room(-14) 同样错（redirect 到 L3 设备时内核自己会去 L2 头，再剥就多剥 14 B，实测抓包：外层 total_length=66 应为 80）——两条路都是错的，只留 redirect（含 L3 回程续租语义等共 7 项差异，逐项见 ADR-0065 偏离清单）。

ringbuf 事件通道。event_ringbuf（256 KiB）+ SodaEvent（72 B，对照 struct dae_event）+ 5 类事件（blocked / UDP 溢出 / TCP 溢出 / rebind 拒斥 / redirect 更新失败；类型 3/5/6/7/9 保留未实现）+ 1 s/键限速 + 丢弃计数；热路径 printk 全部退出（--ebpf-debug 门控保留）。用户态常驻 ebpf-events 线程消费：1 条/秒/类型日志限速，status 增 events（consumed/suppressed/by_type/dropped_kernel）、metrics 增 9 项。限制：内核侧限速是 per-CPU 的（上界 = CPU 数/秒/键），dae 是全局 CAS 严格 1 条/秒——原因是 bpf 目标无 64 位原子 RMW（rustc --print cfg --target bpfel-unknown-none 实测只给 target_has_atomic_load_store）。

skb_send_sock 记账。fentry 优先、kprobe 回退挂同一函数（共用 account() 主体）；aya 无 CO-RE 字段访问，替代物是 loader 侧 btfoff.rs 的最小 BTF 解析器（纯 std，从 /sys/kernel/btf/vmlinux 解出 sk_buff 字段偏移写 trace_param_map，数据面用 bpf_probe_read_kernel 读）——真机 6.18 解得 network_header=184 / transport_header=182 / tail=188 / head=200，与 pahole 逐项一致。先查 offload_guard 过滤（只记本进程注册的 offload 键），再 per-CPU 累加 offload_sent；键摘除时回收进 status.offload_sent.{reclaimed_bytes, kernel_bytes, account_drops}。边界：只做计量，未做 dae 的 per-key 背压 fuse（登记为余项）。

XDP 计量探针。sodama_xdp_observe 恒返回 XDP_PASS、只计数（包 / 字节 / IPv4 / IPv6 / 其它），--xdp <iface> 可选挂载、失败仅告警；status.xdp 区分「0 包」与「没有探针」。定位是 C4 的最小计量探针——数据面搬 XDP 仍维持 §8.3 的否决。

实测口径。本机构建 + section/符号/map 容量核对（event_ringbuf=262144、event_rate_map=259、l3_ifindex_map=64、offload_sent=8192、xdp_stats_map=8、sodama_stats_map=16；SodaEvent=72 B）；cargo test 302/302；musl x86_64 交叉构建 sodama 7.7M · sodama-ebpf 772K（eBPF 对象 496K → 772K）；clippy 无新增 error。内核级：QEMU 内核矩阵（7.2.8）verify 12/12 PASS（含 l3 端到端）、fentry 挂载与记账计数实测、xdp 计数实测；并借此抓到并修掉四处真实缺陷：探针版本字节误读（head+0 → head+nh，parse_fail 由 100% 归零）、L3 回程多剥 14 B（改为只 redirect）、回显夹具 8 次读上限（>32KB 必 RST，曾误诊为 MTU 问题）、net_offload.py 指针段错误（id(buf) 当内核指针）。本批先入库、暂未部署：生产部署会切断当前 72h 窗口（§8.6 世代）并重置计数，时机由用户决定（devlog §19）。
